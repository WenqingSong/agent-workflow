# Workflow V3.4.0 — 独立 Session 协作与轻量化交接

V3.4.0 的目标是让 Agent 之间**通过 Task 协作，而不是通过 Prompt 协作**。

在 V3.3 中，任务事实已经写入 Task Artifact，但交接仍要求上一个 Agent 编写十项 `HANDOFF_PROMPT`。V3.4 删除了这一要求，改为：角色在全新 Session 中只凭「角色名 + Task 目录」启动，自行推导阶段、模式与入口 Gate；结束时只输出四行定位信息。

## 主要变化

### 1. 独立 Session 启动协议

`WorkflowAgentDirective.md` 新增 §2.1 Session Bootstrap Protocol：

```text
以 CLEANER 角色执行任务：
.agent/tasks/<task-slug>/
```

- 角色按固定五步读取规范链、读取 Task 全部现存 Artifact、推导 stage / mode / 入口 Gate、输出五行**开工声明**、运行入口 Gate；
- 推导冲突、`route` 缺失或 Artifact 自相矛盾 → `BLOCKED`，不猜测、不改角色；
- 历史交接块中的 `HANDOFF_PROMPT` 不再作为事实来源。

### 2. 阶段推导表与 `mode` 推导

`WorkflowAgentDirective.md` §2.2 给出由五个 Gate 反推的唯一阶段表（`IMPLEMENTATION_PENDING` / `CONTRACT_PENDING` / `REVIEW_PENDING` / `DECISION_PENDING` / `DELIVERY_PENDING` / `INTEGRATION_PENDING` 等），并标注唯一不可机器推导的组合：Owner `REJECTED` 的退回对象只能读 `owner-decision.md` 的 `Return To`，缺失时 `BLOCKED`。

§2.3 定义七个角色的 `mode` 推导；`finding_ids` 不再是输入，复审对象固定为 `findings.md` 中 `Status: OPEN` 的编号。

### 3. 四字段交接

`WorkflowHandoffContract.md` v2：

```text
RESULT: <本角色终态>
NEXT_ROLE: <下一角色>
TASK_PATH: .agent/tasks/<task-slug>/
OWNER_ACTION: <NONE | CONTINUE | DECIDE: ... | DO: ... | STOP>
```

- 删除 `HANDOFF_PROMPT`、`NEXT_TARGET`、`CURRENT_ROLE` 与十项模板；
- 覆盖矩阵从 8 列瘦身为 7 列（移除 `prompt`）；
- 新增 `STOPPED` 终态（终止 ≠ 阻塞，不写 `blocked.active`）；
- 新增反模式清单：交接块不得复述 AC、40 位 SHA、文件清单、实现步骤或 Gate 前置条件。

### 4. 失败原因持久化

- Cleaner `CHANGES_REQUIRED` → `findings.md`；
- OwnerGate `REJECTED` → `owner-decision.md`（含 `Return To`）；
- Deliverer `FAIL_*` → `delivery.md`；
- Coder / Analyst / Architect / TaskBuilder 失败 → `loop-ledger.md`，新增 `handoff_target` 与 `receiver_action` 两个必填字段。

任何 `FAILURE_HANDOFF` 在发出前必须已落盘并 push；写入失败只能输出 `STOP`（`PERSISTENCE_FAILURE`）。`loop-ledger.md` 属于 Review-neutral 与 Delivery-neutral，不会使既有 `CLEAN` 或 `PASS` 失效。

### 5. 七个 Role 全面适配

七个角色统一使用「角色 + Task 目录」输入与四字段输出。Coder 的必读清单补齐 `findings.md` / `owner-decision.md` / `delivery.md` / `loop-ledger.md`；Architect 补齐 `findings.md`；TaskBuilder 增加 `UPDATE_COMPLETE` 终态、CLEAN 失效说明与循环熔断计数动作。

### 6. TaskBuilder 更新路径

`mode: owner_update` 的输入仍是 `task_path` + `owner_decision`（+ 可选 `extra_instruction`）。新增终态 `UPDATE_COMPLETE`：

- 改动影响实现或验收 → `NEXT_ROLE=CODER`（`coder-start`）；
- 改动的是 Contract / Design 前提 → `NEXT_ROLE=ANALYST`；
- **不存在** `UPDATE_COMPLETE → CLEANER`：`task.md` 不在 Review-neutral 白名单，任何变更都使既有 `CLEAN` 在 `owner-gate-start` 失效。

## 兼容性

| 项 | 状态 |
| --- | --- |
| 五个 Gate（`coder-start` / `cleaner-start` / `owner-gate-start` / `delivery-start` / `merge-ready`） | 语义、名称、exit code 不变 |
| `.agent/engine/**` | 零改动 |
| `state.yaml` schema | 仍为 `3`，无新增字段、无需迁移 |
| 旧式交接块 | 只取 `NEXT_ROLE` / `TASK_PATH` / `OWNER_ACTION`；`HANDOFF_PROMPT` 忽略 |
| 旧式启动串（`mode:` + `task_path`） | 作为覆盖提示；与推导冲突 → `BLOCKED` |
| 旧 Task 无 `route` | 不推断，要求 Owner 显式指定角色 |

新增覆盖：

- 静态：四字段契约、七列矩阵、出口表与矩阵逐项相等、`STOPPED` 存在性、反模式、阶段表覆盖 `state.go` 枚举、无 `mode` 必填、Coder 读取清单；
- 行为（真实 Git + 真实 `workflow-check`）：`GL-14` 只读 Task 目录与 Git 得到全部审查事实；`GL-15` 失败交接写入 `loop-ledger.md` 后可从 Git 恢复且不破坏 `CLEAN`；`GL-16` `task.md` 变更使既有 `CLEAN` 失效。

## 已知边界

- 启动协议、推导表与四字段交接是**规范层约束**；Engine 不解析交接块，不能证明 Agent 遵守。
- 真实 LLM 冷启动验收需人工在独立 Session 中执行并记录；静态测试不能替代。
- 本仓库是框架源码分发包，`dist` 构建要求工作区无未跟踪文件且拒绝 tracked 的 `.agent/tasks/**`；开发期 Task 证据在发布提交前从工作树移除，历史仍可在发布前的提交中追溯。
- `v3.4.0` Tag、Release、SHA256SUMS 与发布 binary 由 Tag 推送触发的 CNB 流水线产生；本文件不预先声称平台已发布。
