# Workflow V3.1.0 Release Notes

> 面向 Workflow 使用者的正式发布说明。本文描述目标版本 `v3.1.0` 的内容；
> 在正式 Tag 创建之前，源码版本 `3.1.0` 只能视为**发布候选**。

| 项目 | 值 |
| --- | --- |
| Source Version | `3.1.0` |
| Source Commit | 构建时由 `git rev-parse HEAD` 注入（完整 40 位 SHA，不写死） |
| Release Tag | `v3.1.0`（发布时创建，本文不声称已存在） |
| Published Status | `NOT_RELEASED` |
| 上一版本 | `v3.0.0` |

## 1. 升级前必读

V3.1.0 是 **Workflow 协议与安装机制的兼容性收紧版本**，不是纯文档更新。升级到本版本前请确认：

1. 新写入的所有 Evidence 必须使用**完整 40 位 Commit SHA**；
2. 旧 Task 中若含 `HEAD`、分支名、可移动 Tag 等**可移动引用**，升级后相关 Gate 可能拒绝沿用旧结论（见 §8）；
3. 升级工具只做受控写入，不会自动改写历史 Evidence，也不会让旧的 `CLEAN` / Owner Acceptance 自动复活。

## 2. 从 V3.0.0 升级的主要变化

| 领域 | V3.0.0 | V3.1.0 |
| --- | --- | --- |
| 角色 | 六角色 | **七角色**：`NORMAL` / `COMPLEX` 六角色 + `ARCHITECT` 路线的 Architect |
| 路线 | `NORMAL` / `COMPLEX` 交接存在断点 | `NORMAL` / `COMPLEX` 全链路交接契约修复 |
| 任务分支 | 由 Owner 手工创建 | TaskBuilder 可执行**受控初始分支**创建（`TB-BRANCH-1`） |
| Agent 指令 | 与宿主规则边界模糊 | 独立 `WorkflowAgentDirective.md`，显式激活与作用域隔离 |
| 循环治理 | 无机器化两轮预算 | **两轮循环熔断 + DANGER 停机 + Owner 恢复**（`WorkflowLoopCircuitBreaker.md`） |
| Evidence | 字符串绑定较宽松 | 不可变 Commit 解析（E-2）、非法引用分类拒绝（F-03） |
| 安装 / 升级 | 手工复制 | Source Distribution + 首装 + B/L/N 三方升级 + 事务回滚（`workflow-adoption`） |
| 版本可核验 | 无 | `workflow-check version` 输出 Binary 版本、Source Commit 与构建来源 |
| 发布资产 | 无正式资产契约 | 四平台 Binary、Source Distribution、`SHA256SUMS`、`version.json`、Release Notes |

## 3. NORMAL / COMPLEX 流程修复

- 修正 TaskBuilder → Analyst → Coder → Cleaner → OwnerGate → Deliverer → Owner Integration 的交接契约，补齐每个角色读取、产出与停止条件，避免上一角色越界接管下一角色。
- 交付与审查绑定关系不再依赖会话记忆：`review.target`、`owner.review_target`、`delivery.feature_head`、`delivery.develop_base` 均绑定明确 Commit。
- `merge-ready` 只表示机器条件满足，最终合并仍由人类 Owner 决定。

## 4. ARCHITECT 第七角色

- 新增 `ARCHITECT` 路线：`TaskBuilder → Analyst → Architect → OwnerGate（结构验证 → Owner 决策）→ Deliverer → Owner Integration`。
- Architect 在已批准 Contract 内交付**结构成果**：模块与职责边界、接口与依赖方向、结构骨架、可复现的结构验证、`architecture.md`。
- ARCHITECT 路线**不经过 Cleaner**，由 OwnerGate 的独立结构验证阶段取代 Cleaner 的结构审查。
- Architect 不实现完整业务功能，不宣布审查通过或最终接受；未实现的业务行为必须登记为 `NOT_EXECUTED`，不得被结构性通过掩盖。
- 角色总数因此为七个。角色数量不是质量指标，路线决定实际启用的角色。

## 5. TaskBuilder 受控初始分支（TB-BRANCH-1）

- TaskBuilder 可在明确授权下创建任务初始分支，并记录分支名、基线 Commit 与授权来源。
- 该能力是**受控**的：不改变 Owner 的合并权，不允许 TaskBuilder 推送业务实现，也不允许其绕过 Gate。
- Owner Action 不包含 `TB-BRANCH-1` 的分支创建；Owner 仍是 Shared Repository Authority。

## 6. Workflow Directive 隔离

- Workflow 专用入口统一为 `.agent/specs/WorkflowAgentDirective.md`，文件名刻意不使用 `AGENTS.md`，避免与宿主的目录级自动加载规则混淆。
- Directive 只适用于被**明确激活**的 Workflow Role Session；普通 Agent 不会被套用 Workflow 的 Git 白名单、Gate 与 Handoff 约束。
- Directive 缺失或不可读时，角色必须输出 `BLOCKED`，不得凭记忆继续。
- 宿主根 `AGENTS.md` 属于宿主项目：存在时读取并遵守，不存在时不创建、不阻断。

## 7. DANGER 两轮协议

- 新增 `WorkflowLoopCircuitBreaker.md`：同一 `(task_id, loop_key)` 在当前 segment 只有**两轮预算**。
- 第二轮后问题仍阻塞时，角色必须生成 `danger-report.md`、追加 `DANGER` 事件、置 `state.blocked.active=true`，输出 `RESULT=DANGER` 并停止，不再 Handoff。
- 明确禁止换措辞、换 Finding ID、拆 Finding、换 Session、换角色或换分支来重新获得预算。
- Owner 恢复必须基于账本事实，不能用一句模糊回复重置轮次。

## 8. Evidence 安全加固

- E-2：Evidence 中的 Commit 字面值必须能唯一解析为真实 Commit，比较统一归一化为完整 SHA。
- 兼容矩阵：

| Evidence 字面形式 | Engine 行为 | 升级处置 |
| --- | --- | --- |
| 完整 40 位 SHA | 接受 | 无需处理 |
| 7～39 位十六进制短 SHA（历史合法） | 接受并解析为完整 SHA | 报告 `legacy_short_sha`；新写入必须用完整 SHA；不自动改写 |
| 不存在 / 有歧义 / 指向非 Commit 对象 | 拒绝 | 报告 `invalid_commit_sha`；Task 标记重新核验 |
| `HEAD` / `HEAD~1` / 分支名 / 可移动 Tag / `origin/*` | 拒绝 | 报告 `invalid_immutable_ref`；Task 标记重新核验 |

- F-03：升级遇到历史非法 Evidence 时，只报告与标记 `task_reverification_required`，**不改写** `state.yaml`，不把旧结论“修好”成活证据。
- 历史合法短 SHA 仍兼容；但短 SHA 兼容不构成新任务使用短 SHA 的许可。

## 9. 安装、升级与来源追溯

- 新增 `.agent/adoption/workflow-adoption`（Python 3.10+，仅标准库）：`dist` / `inspect` / `install` / `upgrade` / `verify` / `restore`。
- 首次安装按包内 `MANIFEST.json` 写入 `managed` 文件，生成真实 `.agent/workflow.yaml`、`.agent/upstream.yaml` 与 `.agent/bin/workflow-check`。
- 升级使用 `.agent/upstream.yaml` 记录的精确 B 快照做 B/L/N 三方比较；快照缺失为 `BASE_UNKNOWN`，不得用远端 HEAD 代替。
- 冲突、B 缺失、删除未授权时 fail closed，整次事务回滚，备份保存在 `<git-dir>/workflow-adoption/backups/<txn>/`。
- 宿主保护对象永不覆盖：根 `AGENTS.md`、根 README、CI、业务 Design、`.agent/workflow.yaml`、`.agent/tasks/**`、`.agent/registry/**`。
- 安装 / 升级只由成功事务写 `upstream.yaml`；正式 Tag 创建前 `source.release` 为空。
- 外部 Binary 必须同时提供 `--workflow-check-sha256` 与 `--workflow-check-commit`，且 Commit 必须等于分发包 Commit。

## 10. 版本命令与发布资产

- 新增 `workflow-check version` 与 `version --json`：

```text
framework: agent-workflow
framework_version: 3.1.0
binary: workflow-check
binary_version: 3.1.0
source_commit: <40-hex>
build_source: release
go_version: go1.24.1
platform: linux/amd64
goos: linux
goarch: amd64
```

- 版本与 Commit 由发布构建通过确定性的 ldflags 注入（`-X main.version` / `-X main.commit` / `-X main.buildSource`），不写死 SHA，不嵌入构建时间。
- 本地 `go build` 的开发构建输出 `dev` / `unknown` / `dev`，不会被误认为发布资产。
- 安装后的 `.agent/bin/workflow-check` 同样自证来源：从分发包 Engine 构建时为 `build_source=source`，使用发布资产安装时为 `build_source=release`，两者都可核对版本与 Commit。
- 升级不会无条件替换宿主的 binary：若本次升级未提供经过校验的新 binary，`workflow-check version` 仍报告**该 binary 的构建 Commit**；已安装分发包的 Commit 以 `.agent/upstream.yaml` 的 `source.commit` 为准。两者不一致时以 upstream 记录判断“安装了什么版本”，以 `version` 判断“这个可执行文件来自哪个 Commit”。
- `version` 不读取 `.agent/workflow.yaml`，也不解析仓库根；在任意目录可运行。
- 正式 Release 附件共 **9 项** = 7 项业务资产 + 2 项校验元数据，全部随 Release 提供：

| 资产 | 类别 | 说明 |
| --- | --- | --- |
| `workflow-check_3.1.0_linux_amd64` | 业务 | Linux x86-64 |
| `workflow-check_3.1.0_linux_arm64` | 业务 | Linux ARM64 |
| `workflow-check_3.1.0_darwin_arm64` | 业务 | macOS Apple Silicon |
| `workflow-check_3.1.0_windows_amd64.exe` | 业务 | Windows x86-64 |
| `agent-workflow-src-3.1.0.tar.gz` | 业务 | Source Distribution（含 `MANIFEST.json`，顶层目录与清单记录完整 Commit） |
| `agent-workflow-src-3.1.0.tar.gz.sha256` | 业务 | Source Distribution 校验文件 |
| `agent-workflow-release-notes-3.1.0.md` | 业务 | 本发布说明 |
| `SHA256SUMS` | 校验元数据 | 覆盖 4 个 Binary、源码包、源码包校验文件与 Release Notes（7 项业务资产） |
| `version.json` | 校验元数据 | 版本 / Tag / Commit / 仓库来源 / Go toolchain / 构建参数 / 平台矩阵 / 7 项资产摘要 / `SHA256SUMS` 摘要 |

- `SHA256SUMS` 不覆盖自身与 `version.json`；`version.json` 记录 `SHA256SUMS` 摘要并自排除，清单可独立校验，不存在哈希环。
- 上传前会生成 9 项附件的固定快照（逐项 SHA256），平台侧重新下载后与快照逐项比较；
  缺少 `SHA256SUMS` 或 `version.json` 任一项、名称重复、大小或哈希不符，发布流程一律 FAIL，
  不会 promote 到 GA，也不会标记 latest。
- 附件名全部为精确文件名（Source Distribution 使用版本号命名），下载不依赖通配匹配。

## 11. Binary 平台支持

| 平台 | GOOS / GOARCH | 验证等级 |
| --- | --- | --- |
| Linux x86-64 | `linux` / `amd64` | `runtime`：构建环境真实执行 `version` |
| Linux ARM64 | `linux` / `arm64` | `static`：交叉编译 + ELF 架构 + Go buildinfo |
| macOS Apple Silicon | `darwin` / `arm64` | `static`：交叉编译 + Mach-O 架构 + Go buildinfo |
| Windows x86-64 | `windows` / `amd64` | `static`：交叉编译 + PE 架构 + Go buildinfo |

构建参数固定：`CGO_ENABLED=0`、`GOWORK=off`、`GOFLAGS=-mod=readonly`、`-trimpath`、`-buildvcs=false`、`-mod=readonly`。

## 12. 重大兼容性变化

1. **Evidence 引用收紧**：`HEAD`、分支名、可移动 Tag、`origin/*` 不再被接受为 Evidence；依赖这些写法的历史 Task 可能被拒绝。
2. **新证据必须用完整 SHA**：短 SHA 仅为历史兼容，不得用于新写入。
3. **升级需要 B 快照**：`.agent/upstream.yaml` 缺失或不可信时升级为 `BASE_UNKNOWN`，不会猜测基线。
4. **角色扩展**：角色数从六个增加到七个，`ARCHITECT` 路线不经过 Cleaner；按角色名硬编码“六角色”的自动化脚本需要更新。
5. **State / Config Schema 不变**：`config_schema = 1`、`state_schema = [2, 3]` 保持兼容，升级不重写历史状态。
6. **Agent 指令入口不变**：仍是 `.agent/specs/WorkflowAgentDirective.md`；宿主 `AGENTS.md` 语义不变。
7. **DANGER 停机是新行为**：以前可以无限次退回/请求的循环，现在第二轮回合后必须停机并交 Owner 恢复。

## 13. 已知限制

1. **Engine 不验证 Agent 身份与 Session 独立性**：独立会话是协作约定，不是机器可验证事实。Engine 只校验可观察的仓库事实与 Artifact。
2. **DANGER 计数不是 Engine 硬限流**：两轮预算由角色 Prompt 与任务账本执行；Engine 只按白名单路径识别账本与 `danger-report.md`，不能证明账本 append-only、轮次真实或报告属实。
3. **历史可移动 SHA 引用升级后可能被拒绝**：`HEAD`、分支名、可移动 Tag、`origin/*` 等旧 Evidence 会被分类拒绝，相关 Task 需要重新核验，不能靠改写字符串让旧结论复活。
4. **历史合法短 SHA 仍兼容**：7～39 位十六进制且能唯一解析的短 SHA 会被接受并归一化；但这不是新任务可以使用短 SHA 的许可。
5. **未实机运行的平台只经过交叉编译与静态检查**：Linux ARM64、macOS Apple Silicon、Windows x86-64 未在真实设备运行，仅校验文件类型、架构与 Go buildinfo，不构成运行时保证。
6. **Adoption 的验证覆盖范围有限**：安装 / 升级的真实 E2E 只在 Linux + Python 3.11 + Git 2.x + Go 1.23+ 的临时 Git 仓库完成；macOS 未在实机验证；Windows 原生环境未验证，需使用 WSL2 / Linux 容器或按规范手工执行。跨项目 Adoption Dogfood 尚未执行。
7. **CNB 平台发布流水线的真实彩排**：发布流水线在发布准备阶段只完成本地构建、失败注入与流水线配置校验；`tag_push → pre-release → 上传 → 验证 → promote` 的真实平台行为需在正式 Tag 推送时最终确认。

## 14. 升级与验证建议

```bash
# 1. 用发布包与校验和安装 / 升级（默认 Dry-run，确认后加 --execute）
.agent/adoption/workflow-adoption upgrade \
  --target /path/to/host \
  --package agent-workflow-src-3.1.0.tar.gz \
  --distribution-sha256 <sha256> \
  --source-commit <full-40-hex> \
  --owner <owner> --owner-authorized --execute

# 2. 校验宿主最终状态（文件、binary、B 快照、真实 Gate 与历史 Evidence）
.agent/adoption/workflow-adoption verify --target /path/to/host

# 3. 核对已安装 Binary 的版本与来源
.agent/bin/workflow-check version

# 4. 校验发布资产（在资产目录内）
sha256sum -c SHA256SUMS
```

升级后如出现 `invalid_immutable_ref` / `invalid_commit_sha`，按 `.agent/specs/WorkflowAdoption.md` §6 的 F-03 流程重新核验对应 Task，不要直接改写历史 `state.yaml`。
