# Workflow V4.0.0 — Lead Agent 负责制与无引擎协作

V4.0.0 是一次结构性重写。它删除了 V3 的工作流引擎与全部程序化流程控制，把流程组织权交还给负责任的主体：**Lead Agent**。

## 为什么重写

V3 用 Go Engine、`state.yaml`、五个 Gate、Stage 推导和 Route 选择来约束协作。运行后发现：

- Gate 通过只说明状态文件合法，不说明代码正确；
- 角色被固化成流水线工位，简单任务过重、复杂任务无法并行；
- 改一条协作规则要先改引擎与 Schema，规则漂移成为常态；
- Agent 倾向于让状态合法，而不是把事做对。

V4 的判断是：流程由负责的 Agent 组织，事实由 Git 与 Markdown 承载，机器只做静态检查。

## 主要变化

### 1. 删除 Engine 与全部程序化流程控制

移除：

- `.agent/engine/`（Go Module、`workflow-check`、Gate 实现、状态加载、Schema 校验）
- `state.yaml` 与 `state_schema`
- 五个 Gate：`coder-start` / `cleaner-start` / `owner-gate-start` / `delivery-start` / `merge-ready`
- Stage 推导表与 Route 选择（`WorkflowRouteSelection.md`）
- 固定交接矩阵与 `HANDOFF_PROMPT`
- `.agent/bin/`、Registry 模板、`workflow.yaml` 模板

这些实现的源码保留在 Git 历史中，V3.4.0 的规范与任务证据归档到 `docs/history/v3.4.0/`。

### 2. Lead Agent 是唯一责任主体

一个任务只有一个 Lead：建档、计划、决定调用哪些角色、保证审查独立、提交与交付。角色是能力边界，可以跳过、并行、多轮，不再有固定顺序。

### 3. 六份 Markdown 工作记录

`task.md`、`plan.md`、`handoff.md`、`findings.md`、`delivery.md`、`decisions.md`。

任何新 Session 只凭「角色名 + 任务目录」启动，读取记录与 Git，输出开工声明后开工。冷启动必须能回答五个问题：目标、已完成、未完成、当前问题、下一步。

### 4. 四字段交接

```text
RESULT: <本次产出与终态>
NEXT: <下一个角色 | LEAD | OWNER | NONE>
TASK: .agent/tasks/<task-slug>/
ACTION: <CONTINUE | DECIDE: ... | DO: ... | STOP | DONE>
EVIDENCE: <可选，最多 2 行>
```

没有落盘的交接不算交接。

### 5. 独立审查可审计

Cleaner 只读，不得审查自己参与实现的变更。审查结论绑定完整 commit SHA；代码变化即失效。无法获得独立审查者时必须在交付记录中标注「独立性未满足」，不得声称已通过。

### 6. 失败处理简化

判断失败类别 → 同一条路径最多两次有依据的尝试 → 升级 Lead → 涉及范围、授权、重大架构与不可逆操作升级 Owner。失败与决策写入 `findings.md` / `decisions.md`。

### 7. 工程工具重写

| 工具 | 能力 |
| --- | --- |
| `workflow-adoption dist` | 从干净 commit 构建确定性源码包，生成 `MANIFEST.json` |
| `workflow-adoption inspect` | 校验包哈希、成员哈希与分类 |
| `workflow-adoption install` | 首次安装，只写 `managed` 文件 |
| `workflow-adoption upgrade` | B/L/N 哈希三方比较，冲突整体失败 |
| `workflow-adoption rollback` | 事务备份回滚 |
| `workflow-adoption verify` | 安装完整性与 V3 残留检查 |
| `workflow-adoption check` | 仓库一致性静态检查（文件、规范、术语、记录） |
| `scripts/release/release.py` | 源码资产、`SHA256SUMS`、`version.json`、发布守卫 |
| `.agent/tools/git-facts` | 只读 Git 事实 |

发布不再构建任何二进制。

## 规范

七份规范重新组织，互不引用已删除机制：

1. `WorkflowAgentDirective.md` — 入口、启动协议、冷启动五问、授权与真实性
2. `AgentCollaborationSpecification.md` — 事实来源、Lead 地位、并行、独立性
3. `Five-AgentResponsibilityBoundary.md` — 七个角色与 Owner 的权责与工具披露
4. `WorkflowHandoffContract.md` — 交接块、记录矩阵、失败交接
5. `WorkflowGitLifecycle.md` — 分支、提交、推送、审查绑定、发布
6. `WorkflowLoopCircuitBreaker.md` — 失败分类、两次尝试、升级与停止
7. `WorkflowAdoption.md` — 分发、安装、升级、回滚、校验边界

## 角色 Prompt

TaskBuilder、Analyst、Architect、Coder、Cleaner、OwnerGate、Deliverer 七个角色全部重写，统一要求：

- 输出开工声明与工具能力；
- 只写自己边界内的记录；
- 结束时落盘并输出交接块；
- 如实报告未执行的操作与未验证的结论。

## Dogfood

`dogfood/ledgerd/` 是用 V4 实际开发的 Go 个人账本 HTTP 服务，保留真实的开发提交、工作记录、独立审查与冷启动验证。它不是模拟对话，代码与测试可在仓库中直接运行。

## 验证

```bash
python3 -m unittest discover -s .agent/adoption/tests -v
python3 -m unittest discover -s scripts/release/tests -v
python3 .agent/adoption/workflow_adoption.py check --repo .
go -C dogfood/ledgerd vet ./...
go -C dogfood/ledgerd test ./... -count=1
go -C dogfood/ledgerd test -race ./... -count=1
```

## 已知限制

- 规范是行为约束，不是机器强制；Agent 可能不遵守，只能通过记录与审查发现。
- 框架不能证明 Session 独立性，只能要求如实声明并留下可审计证据。
- `check` 是静态检查，不验证语义正确性。
- Dogfood 在单仓库内以子项目完成，不等同于多个外部项目的长期接入验证。
- 安装/升级工具仅在 Linux 验证；Windows 需 WSL2 / Linux。

## 升级说明

从 V3.4.0 升级到 V4.0.0 时：

1. `.agent/engine/`、`state.yaml`、`.agent/bin/`、`workflow.yaml` 不再使用，可由宿主删除；
2. 旧的 V3 任务记录不会被修改；新任务使用六份 Markdown 记录；
3. 使用 `workflow-adoption upgrade` 时，本地修改过的规范文件会保留并报告 `kept_local`；若上游同时修改则整体失败，需 Owner 决定。
