# Agent Workflow V4 设计

> 版本：4.0.0
> 状态：已实施
> 本文解释「为什么这样设计」，不重复规范条文。规范以 `.agent/specs/` 为准。

## 1. 问题

V3 用一套机器机制约束多 Agent 协作：Go Engine 读取 `state.yaml`，按五个 Gate 判断能否进入下一阶段，用 Route 选择角色序列，用固定交接矩阵要求上游生成长 Prompt。

运行中暴露出四类问题：

1. **证据错位**：Gate 只证明「状态文件写了 PASS」，不证明代码正确。状态与代码脱节时，流程仍然「绿灯」。
2. **刚性**：角色被固化成流水线工位。简单任务要跑完六个角色，复杂任务又无法并行。
3. **维护成本**：改一条协作规则，要先改 Engine、Schema、测试与文档；规则漂移成为常态。
4. **目标置换**：Agent 更倾向让状态合法，而不是把事做对。

## 2. 设计判断

V4 的核心判断是：

> 流程由负责的 Agent 组织；事实由 Git 与 Markdown 承载；机器只做静态检查。

这不是「减少约束」，而是把约束放到能被验证的地方：

| V3 约束方式 | V4 约束方式 |
| --- | --- |
| 状态文件 + Gate | 真实 Git 事实 + 独立审查结论绑定 commit |
| Route 决定角色序列 | Lead 按任务组织角色 |
| Schema 校验 | 记录模板 + 冷启动五问 |
| 程序化重试预算 | 两次有依据的尝试 + 升级路径 |
| Engine 二进制 | 无需运行时；只需 Git 与 Python |

## 3. 结构

```text
Owner
  │
  ▼
Lead Agent（唯一责任主体）
  ├── 工作记录（6 份 Markdown）
  ├── 专业角色（TaskBuilder / Analyst / Architect / Coder / Deliverer）
  ├── 独立审查（Cleaner，只读）
  └── 决策协助（OwnerGate）
底层：文件、Git、命令执行、Subagent
```

### 3.1 为什么保留 Lead

多 Agent 系统的失败模式通常不是「某个角色不专业」，而是「没有人对结果负责」。V4 明确 Lead 的单一责任：它必须决定调用谁、保证审查独立、维护记录、提交与交付。角色可以缺席，Lead 不能。

### 3.2 为什么角色不是工位

任务规模差异极大。V4 允许 Lead 跳过 Architect、并行多个 Analyst、多轮 Cleaner、让同一角色重复被调用。约束只剩下能力边界与独立性，不再有固定顺序。

### 3.3 为什么用六份 Markdown

| 文件 | 回答的问题 |
| --- | --- |
| `task.md` | 做什么、做到什么程度、基线是什么 |
| `plan.md` | 现在在哪、下一步是什么 |
| `handoff.md` | 谁在什么时候交接了什么 |
| `findings.md` | 有什么问题、修了没有、审查对象是哪个 commit |
| `delivery.md` | 交付了什么、验证了什么、还有什么没验证 |
| `decisions.md` | 谁决定了什么、为什么 |

这六份文件覆盖冷启动五问，且都是人可读、Git 可 diff 的普通文本。没有解析器，就没有「为了让解析器通过而写记录」的动机。

### 3.4 独立性如何保证

机器无法认证 Session 身份。V4 的做法是把独立性写成**可审计的声明**：

- Cleaner 必须声明自己未参与实现；参与则拒绝出结论；
- 审查结论绑定完整 SHA，代码变化即失效；
- 无法获得独立审查时，必须在交付记录中标注「独立性未满足」，不得声称已通过。

这比「假装机器能验证」更诚实，也更可追责。

### 3.5 失败处理

失败分类 → 最多两次有依据尝试 → 升级 Lead → 必要时升级 Owner。

不设程序化预算，因为「重试几次」不是关键；关键是**每次尝试是否有新假设**。规范要求把假设与结果写进 `findings.md`，使重复尝试可被审查。

## 4. 删除清单

| 删除项 | 理由 |
| --- | --- |
| `.agent/engine/` | 运行时状态机不再承担判断职责 |
| `state.yaml` 与 Schema | 状态可由记录与 Git 推导，无需机器副本 |
| 五个 Gate | Gate 结论不等于代码正确，且制造虚假安全感 |
| Stage 推导表 | Lead 直接维护 `Next Action` |
| Route 选择 | 任务复杂度由 Lead 判断，不需要枚举 |
| 固定交接矩阵 / `HANDOFF_PROMPT` | 交接只需定位，事实在记录里 |
| `.agent/bin/` | 没有二进制 |
| Registry | 资源登记改用普通 Markdown（如需要） |

这些实现的源码仍保存在 Git 历史中，V3.4.0 的规范与证据归档在 `docs/history/v3.4.0/`。

## 5. 工程支撑

| 工具 | 职责 | 明确不做 |
| --- | --- | --- |
| `workflow-adoption dist` | 构建确定性源码包 | 不编译任何东西 |
| `workflow-adoption install/upgrade/rollback` | 事务化安装与 B/L/N 升级 | 不碰宿主业务文件 |
| `workflow-adoption verify` | 校验安装完整性与哈希 | 不判断任务是否完成 |
| `workflow-adoption check` | 仓库一致性静态检查 | 不解析任务状态、不调度角色 |
| `scripts/release/release.py` | 源码资产、SHA256、发布校验 | 不构建旧 Engine 二进制 |
| `.agent/tools/git-facts` | 只读 Git 事实 | 不写 Git |

`check` 的边界尤其重要：它检查文件是否存在、规范是否完整、是否残留 V3 术语。它不判断「任务处于哪个阶段」，因此不会演化为新的工作流引擎。

## 6. 发布

```text
annotated tag v4.0.0
  → guard（Tag / 版本 / Commit 绑定）
  → 测试与一致性检查
  → 构建源码包 + SHA256SUMS + version.json + Release Notes
  → 本地校验
  → pre-release 上传
  → 平台侧回读校验
  → promote
  → 复核
  → latest
```

失败任一步即停止，不得标记 GA。发布资产只包含源码，不含二进制。

## 7. 已知限制

1. 规范是行为约束，不是机器强制；Agent 可能不遵守，只能靠记录与审查发现。
2. 独立性依赖 Agent 如实声明；框架不能证明两个 Session 真的是两个主体。
3. `check` 是静态检查，无法验证语义正确性。
4. Dogfood 在单仓库内以子项目完成，不等同于多个外部项目的长期接入验证。
5. 冷启动五问可被机械回答；真正的理解仍需审查者判断答案质量。
